# Sanitar

**Sanitar** — сервис, который находит в тексте секреты (API-ключи, токены, приватные ключи, пароли, строки подключения) и заменяет их. Сценарий использования: человек копирует лог, конфиг или стектрейс, прогоняет его через сервис и вставляет очищенную версию в чат, тикет или AI-ассистент.

## Этапы

1. **Этап 1 (текущий): веб-сервис в docker-compose.** Страница с полем для вставки текста; по клику все найденные секреты заменяются. Цель этапа — проверить гипотезу: насколько хорошо работает детекция и удобен ли UX.
2. **Этап 2 (позже, сейчас не делать): расширение для Chrome**, которое чистит текст при вставке. Оно будет переиспользовать тот же движок детекции.

Из-за этапа 2 движок с самого начала пишется как **отдельный пакет без зависимостей от окружения**: он должен одинаково работать в браузере, в Node и в service worker расширения (Manifest V3).

## Стек

- TypeScript (strict), pnpm workspaces, Node 24 LTS.
- `packages/core`: ноль runtime-зависимостей. Для случайных значений использовать только `globalThis.crypto.getRandomValues`, который есть и в браузере, и в Node.
- `apps/web`: Vite. Без внешних CDN, шрифтов и аналитики: всё отдаётся с нашего сервера.
- `apps/server`: Fastify.
- Тесты: Vitest.

## Детекция

### Источник правил

Правила берём из gitleaks (лицензия MIT; файл `config/gitleaks.toml` в репозитории gitleaks/gitleaks). Версию gitleaks зафиксировать в скрипте импорта. **Не копировать код и детекторы trufflehog**: у него лицензия AGPL.

Скрипт `scripts/import-gitleaks-rules.ts` скачивает TOML нужной версии и пишет JSON со следующими полями для каждого правила: `id`, `description`, `regex`, `secretGroup`, `entropy`, `keywords`, `allowlists`. Сгенерированный JSON коммитится в репозиторий, чтобы сборка не ходила в сеть.

### Подводные камни при конвертации из Go RE2 в JS RegExp

- Inline-флаги: `(?i)` в начале выражения переводить в флаг `i`. Для `(?i)` в середине выражения проверить поддержку модификаторов `(?i:...)` в целевых рантаймах; если её нет, разворачивать вручную или пропускать правило с предупреждением.
- Если в выражении есть конструкции, которые JS не понимает (например, `\z`, POSIX-классы `[[:alnum:]]`), их нужно конвертировать. Правила, которые сконвертировать не удалось, логировать при импорте и не включать в JSON. Нельзя молча ломать.
- Все регулярки компилируются с флагом `g` (для `matchAll`), а при необходимости и `d` (indices), чтобы получать точные позиции `secretGroup`.
- Скрипт импорта в конце компилирует каждое правило и падает, если хоть одно из включённых не компилируется.

### Алгоритм

1. **Keyword prefilter.** Если у правила есть `keywords`, проверяем его только когда в тексте (в lowercase) встречается хотя бы одно ключевое слово. Это главная оптимизация, без неё ~200 регулярок на большом тексте работают медленно.
2. **Match.** Секрет — это `secretGroup`, если она указана, иначе первая непустая группа или весь матч. В находку сохраняем только позиции секрета, а не всего матча.
3. **Entropy.** Если у правила задан порог `entropy`, отбрасываем находки с меньшей энтропией Шеннона.
4. **Allowlists правила** (regexes, stopwords) из gitleaks применяем как есть.
5. **Пользовательские исключения** (см. ниже).
6. **Слияние пересечений.** Если находки перекрываются, объединяем их в одну с самым специфичным `ruleId` (не generic). Generic-правила проигрывают конкретным.

Персональные данные (категория `pii`, файл `rules/pii.ts`): email, телефоны, номера карт (с проверкой Luhn), значения полей `first_name`/`birth_date`/`passport`/`phone`… Опция `pii?: boolean` в `scan`/`sanitize` и в API (по умолчанию `true`), в UI — чекбокс. У `Finding` есть поле `category: "secret" | "pii"`.

Дополнительно в `custom.ts` добавить правила, которых может не быть в gitleaks или которые нам важны: блоки `-----BEGIN ... PRIVATE KEY-----` целиком (многострочные), пароли в URL (`scheme://user:PASSWORD@host`), `password=` / `passwd:` / `secret:` в конфигах и `.env`, `Authorization: Bearer ...`.

### Лимиты

- Максимальный размер входного текста: 1 МБ (константа в core; сервер и фронт её проверяют).
- Защита от катастрофического backtracking: тест производительности на 1 МБ случайного текста и на 1 МБ base64 должен укладываться в разумное время (ориентир — < 2 с). Если какое-то правило тормозит, выявить его в тесте и исключить.

## Замена

Публичный API core:

```ts
type Mode = "placeholder" | "erase" | "random";

interface SanitizeOptions {
  mode: Mode;
  placeholder?: string;          // по умолчанию "<secret>"
  placeholderWithType?: boolean; // "<secret:aws-access-token>"; по умолчанию false
  exclusions?: string[];         // пользовательские regex (исходники строк)
}

interface Finding {
  ruleId: string;
  description: string;
  start: number;   // смещение секрета в исходном тексте
  end: number;
  line: number;    // 1-based
  preview: string; // замаскированное значение: первые 4 символа + "…", для коротких только "…"
}

function scan(text: string, opts?: { exclusions?: string[] }): { findings: Finding[]; excluded: Finding[]; errors: ExclusionError[] };
function sanitize(text: string, opts: SanitizeOptions): { text: string; findings: Finding[]; excluded: Finding[]; errors: ExclusionError[] };
```

Режимы:

1. **placeholder** — секрет заменяется на `<secret>` (или на пользовательскую строку, или на `<secret:RULE_ID>`).
2. **erase** — секрет удаляется (заменяется на пустую строку). Окружение не трогаем: `KEY=abc` превращается в `KEY=`.
3. **random** — секрет заменяется случайной строкой той же длины и того же алфавита: `[a-z]` → случайная строчная буква, `[A-Z]` → прописная, `[0-9]` → цифра, остальные символы (`-`, `_`, `/`, `+`, `=`, `.`) сохраняются на своих местах. Так сохраняется формат (например, у JWT остаются точки), но значение уже не настоящее. Известные префиксы (`ghp_`, `sk-`, `AKIA`, `xoxb-` и т. п.) лучше тоже сохранять, чтобы читатель понимал тип секрета. Префикс берётся из правила, если правило его явно задаёт; иначе заменяем всё.

Замены применяются **с конца текста к началу**, чтобы смещения не съезжали. `findings` всегда возвращаются с позициями в **исходном** тексте.

Секреты никогда не попадают в логи, сообщения об ошибках, `console.*` или ответы API (в ответе только `preview`).

## Исключения (exclusions)

- Пользователь задаёт список regex, по одному в строке.
- Исключение проверяется против **значения найденного секрета**. Если regex совпадает с секретом (через `test`, не полное совпадение), находка попадает в `excluded` и не заменяется.
- Пример: `^AKIA.*EXAMPLE$` оставит в тексте документационный ключ AWS; `^sk-test-` оставит тестовые ключи.
- Невалидный regex не роняет обработку: он возвращается в `errors` с номером строки и текстом ошибки, а остальные исключения применяются.
- Флаги можно задавать в формате `/pattern/flags`; строка без слешей интерпретируется как pattern без флагов.

## Веб-интерфейс (apps/web)

Одна страница:

- Большое поле «Исходный текст» (вставка, а также drag-and-drop текстового файла).
- Переключатель режима: `<secret>` / стереть / случайный текст. Для режима `<secret>` — поле для своего плейсхолдера и чекбокс «добавлять тип секрета».
- Поле «Исключения (regex, по одному в строке)». Невалидные строки подсвечиваются с текстом ошибки.
- Кнопка «Очистить» (и `Ctrl/Cmd+Enter`).
- Поле «Результат» (только чтение) с кнопкой «Скопировать».
- Список находок: тип правила, строка, preview; исключённые — отдельным списком, приглушённо. Клик по находке подсвечивает её место в исходном тексте.
- Счётчик: «Найдено N, заменено M, исключено K».
- Настройки (режим, плейсхолдер, исключения) сохраняются в `localStorage`. **Сам текст в `localStorage` не сохранять никогда.**

**Обработка по умолчанию идёт в браузере**: фронт импортирует `packages/core` напрямую, и текст вообще не уходит на сервер. Это главный аргумент доверия, и его стоит явно написать в интерфейсе одной строкой. HTTP API на сервере нужен для curl/CLI-сценариев и для сравнения, но фронт его не использует.

Дизайн простой и аккуратный, светлая и тёмная тема (`prefers-color-scheme`), адаптивная вёрстка. Язык интерфейса — английский (README тоже на английском). Строки вынесены в `apps/web/src/i18n/en.ts`, чтобы потом можно было добавить другие языки.

### Публикация на GitHub Pages

Страница полностью статическая и публикуется на GitHub Pages (`.github/workflows/pages.yml`: тесты → сборка `apps/web` → деплой). Поэтому:

- в Vite `base: "./"` — пути к ресурсам относительные, сайт работает под подпутём `/<repo>/`;
- Pages не умеет отдавать заголовки, поэтому CSP при сборке вставляется в `<meta>` (`connect-src 'none'`, без `unsafe-inline`/`unsafe-eval`). `frame-ancestors` в `<meta>` не работает — это известное ограничение Pages-версии;
- фронт не должен зависеть от сервера: никаких запросов к `/api`.

## Сервер (apps/server)

- Отдаёт собранный `apps/web` как статику.
- `POST /api/sanitize` — тело `{ text, mode, placeholder?, placeholderWithType?, exclusions? }`, ответ — результат `sanitize()`.
- `POST /api/scan` — только находки, без замены.
- `GET /healthz`.
- Лимит тела запроса: 1 МБ, при превышении ответ 413.
- **Тела запросов и ответов не логируются.** В логах Fastify отключить логирование body; логировать только метод, путь, статус и время.
- Заголовки безопасности: строгий CSP (`default-src 'self'`, без `unsafe-inline`, `unsafe-eval` и внешних источников), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` для `/api/*`.
- Никакой телеметрии и исходящих сетевых запросов.

## Docker

- Multi-stage `Dockerfile`: сборка на `node:24`, рантайм на `node:24-slim` (или distroless). Процесс запускается не от root.
- `docker-compose.yml`: один сервис `sanitar`, порт **`127.0.0.1:8080:8080`** (по умолчанию слушать только localhost), `read_only: true`, `tmpfs` для `/tmp`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, healthcheck на `/healthz`.
- Для контейнера можно указать `network_mode`/отдельную сеть без выхода наружу, так как ему не нужен интернет. Это необязательно, но стоит оставить закомментированным примером.

## Тесты

- **Важно: не коммитить ничего, что выглядит как настоящие секреты.** Push protection GitHub и сканеры заблокируют push или поднимут алерт. Тестовые секреты нужно либо генерировать в рантайме теста (префикс + случайные символы нужного алфавита), либо брать официальные документационные значения (например, `AKIAIOSFODNN7EXAMPLE`). В фикстурах допустимо собирать строки конкатенацией (`"ghp_" + "..."`), чтобы статические сканеры их не ловили.
- Unit-тесты core: на каждый режим замены; исключения (включая невалидный regex); слияние пересечений; многострочный приватный ключ; несколько секретов в одной строке; secretGroup (заменяется только секрет, а не `KEY=`); позиции в исходном тексте; пустой текст; текст без секретов возвращается без изменений байт в байт.
- Тест «нет ложных срабатываний» на типичном безобидном тексте: git-хэши, UUID, обычный код, markdown. Ложные срабатывания не обязательно должны быть нулевыми, но тест фиксирует текущее число и не даёт ему расти незаметно.
- Тест производительности (см. «Лимиты»).
- Тест сервера: `/api/sanitize` работает, 413 на большой body, тело не попадает в логи.

## Заметки для этапа 2 (не реализовывать сейчас)

- Расширение Chrome MV3 импортирует `packages/core` как есть. Поэтому в core нельзя использовать `window`, `document`, `Buffer`, `fs`, `process` и т. п. Это проверяется линтером или тестом сборки core для target `webworker`.
